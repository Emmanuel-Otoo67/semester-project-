# LibTrack Attendance Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add student programme/level data and a secure staff-operated library attendance workflow without disturbing existing circulation.

**Architecture:** Reuse `members` and add an attendance domain in Spring Boot backed by additive PostgreSQL migrations. Staff UI calls the API through existing `apiFetch`; visit rules are enforced transactionally in Java and with database constraints. This first slice uses staff-operated manual lookup; kiosk authentication and student QR are subsequent reviewed slices.

**Tech Stack:** Java 21, Spring Boot 3.5.7, Spring Security, JDBC, PostgreSQL/Flyway, React 18, TypeScript, Vite, Vitest, JUnit/Mockito.

**Spec:** `docs/superpowers/specs/2026-11-24-libtrack-smart-library-design.md`

## Global Constraints

- Preserve existing React/Vite + Spring Boot architecture and current staff authentication/roles.
- Preserve existing member, catalogue, copy, loan, hold, settings, staff, audit, and dashboard behavior.
- Use additive migrations; do not test against production Supabase.
- Keep all application data access behind the Java API.
- Use Africa/Accra for library display timezone; timestamps are generated by PostgreSQL/server.
- Preserve supplied LibTrack black, orange-yellow, and white brand identity.

## Review Focus

- Concurrent check-ins for one student must produce only one open visit.
- Checkout with no open visit must fail without creating or mutating a visit.
- Inactive or non-student members must not be checked into student attendance.
- Search/filter values must be parameterized and empty/invalid date ranges handled explicitly.
- A runtime role with current RLS grants must be able to use the new table without granting browser roles direct access.
